# Interface modes and review status

## Commercial versus emulated Wi-Fi provisioning

Commercial SkyPortal accessories are configured using Celestron's SkyPortal app:
connect directly to the module, use its communication settings to configure the
router network, then select access-point operation and move the module switch to
its WLAN position. Reconnect the phone to the same router. Follow the illustrated
[Celestron manual](https://celestron-site-support-files.s3.us-east-1.amazonaws.com/support_files/93973_Celestron%20SkyPortal%20WiFi%20Accessory_Manual_5LANG_2022.pdf)
for your model; do not assume identical switch orientation across products.
This is the manufacturer's procedure. This app additionally offers experimental TCP 3000 provisioning, described below.

Emulated modules may instead provide a captive Wi-Fi setup hotspot or browser
configuration page. Use that firmware-provided method as an optional alternative when applicable.
Do not send legacy WiFly commands to modern modules. The identified ESP32 has
an Open module Wi-Fi setup page button. Its hotspot address may differ from its
router-assigned address. Follow the firmware instructions, then reconnect and
rediscover after network changes. A web portal is not assumed for all modules.

Celestron Telescope Network Control controls telescopes over Wi-Fi (WiFi),
through direct/ad hoc or infrastructure networks. Its specialized legacy
support covers the Celestron COSMOS 90GT WiFi Telescope with the V1 WiFly / SkyQLink RN-171
module. The existing package and command names remain compatible.

| Selected interface | Motor control | Control Bridge | Provisioning and diagnostics |
| --- | --- | --- | --- |
| SkyQLink (Celestron V1) | Direct AUX over the legacy connection | Available | WiFly configuration and AUX reads |
| Celestron module (V2 or later) | Direct AUX; no legacy restart sequence | Disabled; connect your astronomy app directly | AUX diagnostics; settings only when supported; no legacy WiFly writes |
| Controller proxy (diagnostic) | Disabled | Disabled; no chained bridge | Management identity and cached position diagnostics only |

Click Discover SkyQLink / Celestron Modules, choose a result, then click
Apply Module & Profile. The Recommended communications profile box automatically selects the detected profile.
You may override it before clicking Apply Module & Profile. A positively identified
controller proxy remains diagnostics-only even if another profile is selected. Discovery alone does not
change the active target. For an unclassified endpoint, choose a profile explicitly before applying it. Absence of a proxy
signature does not prove that a device is physical hardware. The ESP32 simulator
represents the modern Celestron interface during development; its advertised
identity is appended to the modern-module label. Simulator checks do not establish
compatibility with every commercial Celestron adapter.

The known ESP32 has its own HTTP setup page, available from Wi-Fi provisioning.
Our updated ESP32 source supports the desktop configuration form; older firmware
requires its portal. Commercial AMW007/ZentriOS configuration is experimental
and requires explicit opt-in; use the manufacturer procedure if unsupported. Missing
backlash replies appear as Not reported; modern backlash writes require readable
values before transmission. Raw encoder references are not celestial alignment.
Controller proxy diagnostics use TCP 3000 management, never the motor data port.
Older proxy versions may not support cached telemetry; this is reported as such.

## Logs and offline export

Network Transfer Log shows commands generated by this control app, including
motor moves, stops and background reads, plus connection notices. Communications
Log includes external client traffic, this app's traffic and telescope replies.
Entries include timestamps, network origin and destination where available,
raw AUX hex and known interpretations. Credentials are redacted.

Copy as CSV exports displayed rows with quoted fields. Export CSV opens the
recording export dialog for the saved data and selected time range. Display
buffers are bounded; use saved recordings for the complete session. A reply's
request purpose is inferred when one recent request matches, ambiguous when
several match, or unknown. AUX has no transaction ID; this is not proof of who
caused motor motion.

Save All Logs creates a ZIP snapshot of all files under the session-log directory.
Open Saved Logs accepts JSON, JSONL or a ZIP containing multiple session folders.
It previews and exports offline without connecting to the telescope or extracting
the ZIP. Nested folder names remain in exported source-session identifiers.
Active sessions can end with an incomplete final record; inspect export warnings.
Archive import is limited to 256 MiB per member and 512 MiB total.

## Review limits

Windows GUI review is complete; real-device validation remains separate. Prior COSMOS 90GT
motion tests remain separate from verification of this revision. Pi installation, startup and focused offline tests passed on Buster/Python 3.12.16.
Commercial modern-module hardware and new macOS rendering have not been retested. Do not infer universal compatibility from discovery.

## Bridge controls by profile

For Celestron module and Controller proxy (diagnostic), the entire Control Bridge
tab is disabled and its red/green status icon is removed. Diagnostics instead
shows the selected endpoint/profile, local adapter inventory, current transfer
log and saved-log open/save/export tools. Module identity and available proxy
cache data remain in the read-only diagnostic results. These extra panels appear
only for these profiles. Returning to SkyQLink restores the bridge tab and icon.

Two Interface Mode,
bridge binding address, heartbeat, position recording and local-jog polling
controls are disabled. Their associated polling explanations are dimmed.
Log viewing/copy/export and network-adapter inspection remain available.
For SkyQLink, polling settings can be prepared while the bridge is OFF; no
bridge polling runs until it is ON. Local-jog feedback polling additionally
requires local jogging to be enabled. Two Interface Mode and binding address
cannot be edited while a connection or another operation owns the endpoint.
Direct Motor control has its own polling settings; bridge settings do not
configure a direct modern-module motor connection.

## Modern-module Motor control

The Celestron module profile keeps Motor control available. Click Connect Motors
for direct Celestron AUX communication over the module's Wi-Fi TCP connection.
Jog/Stop, encoder readback and idle release remain on Motor control;
modern direct polling controls are in Diagnostics; no bridge is started. Controller Angle / Backlash Settings opens the
hardware-settings view by default for this profile, with both axes visible.
Read the current values before adjusting encoder reference, absolute backlash or
backlash delta. Disconnect Motor control and other controllers before using this
exclusive settings operation. Position reference writes change the raw encoder
origin without moving the mount; they do not establish celestial alignment.

The command family is AUX for both legacy and modern motor controllers. Modern
mode bypasses legacy WiFly greeting/restart/provisioning behavior. Supported
writes require acknowledgement and matching readback. Missing backlash replies
remain unavailable; simulator support does not prove every commercial mount
implements those settings. The Controller proxy (diagnostic) profile intentionally
does not expose motion or settings writes.

### Modern polling controls in Diagnostics

For the modern Celestron profile, Diagnostics → Motor polling / keep-alive and recording edits the same polling enable/interval values used by Motor control.
Motor control shows the configured values while disconnected and the applied
values during a connection. Disconnect, edit, then reconnect to apply changes;
the fields are disabled during a connection. No additional socket or scheduler is
created. Position replies are already recorded by the motor service. This one
polling option provides both idle keep-alive and position recording; it does not
reset the independent idle-release timer. Movement feedback remains active even
with idle polling OFF. SkyQLink retains its original direct and bridge controls;
the controller-proxy profile never starts motor polling.

## Cord wrap, GoTo approach and travel limits

Motor control → Controller Angle / Backlash Settings → Telescope controller →
Cord wrap / GoTo approach / limits provides per-axis approach selection and
azimuth-only cord-wrap enable/disable and raw boundary angle. Read current values
first; unsupported/unreported controls stay grey. A successful read permits an
attempted write, not a promise of firmware support: every write is checked again
and requires acknowledgement plus matching readback. No actual hardware writes
were performed while developing these controls; offline protocol tests cover
both communications profiles. The current ESP32 simulator does not implement
these endpoints, so these controls should stay disabled on it.

Both Wi-Fi families transport the same motor AUX commands: approach read/write
0xFC/0xFD (0 positive, 1 negative); azimuth cord-wrap enable/disable 0x38/0x39,
boundary write/read 0x3A/0x3C, enabled read 0x3B (00 off, FF on). These are motor
endpoints, not WiFly settings. See the original
[AUX command reference](https://paquettefamily.ca/nexstar/NexStar_AUX_Commands_10.pdf),
Motor control commands and Controlling Cordwrap. Approach changes the final GoTo
approach direction; it does not reverse jog keys. Cord-wrap boundary accepts
0–360 raw degrees, up to five decimals. It is not a celestial coordinate.

Minimum/maximum elevation or manual-jog travel limits remain unavailable here:
no verified writable AUX endpoint was established from the observed app sliders.
Do not treat cord wrap as a guaranteed manual-motion hard stop. Host-side tracking
limits and mechanical stops are separate. Controller proxy remains read-only.

### Communications-log arrows

Network arrows show forwarding order: External control app → This control app →
Telescope, or Telescope → This control app → External control app. Locally
originated requests begin at This control app. Received packets without a
successful client forward say not forwarded. AUX-header arrows describe the
source/destination bytes inside the packet, not the network route: a returned
request echo retains the original controller-to-motor header. This is not a
second outgoing command. Response requester attribution remains inferred or
ambiguous, because AUX has no transaction identifiers.

### Active profile and scrolling

The Applied profile / Target readout identifies the configuration currently in
use. A highlighted discovery result and Recommended communications profile are
pending until Apply Module & Profile is clicked. Disconnect the motor connection or
switch Control Bridge OFF before applying another module.

Live logs follow new entries while scrolled to the bottom. Scrolling upward
preserves the visible record until you return to the bottom. Each log viewer
maintains its own scroll position. If a viewed record ages out of the bounded
display buffer, use saved-log export for older history. The implementation avoids
Text.see, which was observed hanging inside Windows Tk during bridge log updates.
New GUI batches are time-bounded so incoming traffic cannot monopolize input.

### Post-jog button lock

Releasing a jog sends Stop, then compares encoder samples before enabling another
movement. The sampling includes a 0.25-second settling interval; additional
settling or missing replies can take longer. ESP32 simulator logs on 2026-11-18
showed position replies typically around 10 ms and post-jog verification around
0.3 seconds, not a deliberate multi-second simulator delay. GUI event handling
now resumes queued bounded batches after 1 ms instead of adding a 100 ms wait to
every batch. This removes a potential display backlog without bypassing stop
verification. Live perceived responsiveness still needs retesting after relaunch.

Modern-profile Diagnostics places Motor polling / keep-alive and recording at
the top, before read-only query results. Controller Angle / Backlash Settings
is available only on Motor control, including the cord-wrap and GoTo approach
submenu. Diagnostics does not duplicate that settings menu. Time/location writes are explicitly unavailable
for this profile until documented, compatible endpoints are verified; optional
GPS/RTC readbacks do not establish writable site/time support.


## Modern-module Wi-Fi configuration (experimental, 2026-11-18)

The Celestron module profile now has SSID, masked password, network security,
Read module Wi-Fi settings, and Apply & Save Router Wi-Fi Settings controls.
Disconnect Motor control/Control Bridge and finish other operations first.
Read obtains the SSID, not the password. Enter a password before Apply; an
explicit Open selection requires an empty password. Personal encryption is
negotiated automatically using a method supported by both device and router.
This is not a claim of WPA3-only, WEP or Enterprise support. Quotes, backslashes
and control characters are currently rejected rather than guessing escaping rules.

Our ESP32 source v0.2.3 implements the management configuration capability and
uses the same saved record as the captive portal. Some emulated modules offer
captive Wi-Fi setup pages as an alternative; the project includes our ESP32
portal code. Existing v0.2.2 firmware does not support desktop provisioning:
use its portal until the new firmware has been compiled, tested and uploaded.

Desktop writes stage SSID/passkey and enable DHCP, check staged SSID readback,
then save. On our ESP32, station mode is selected in software and saving schedules
a restart. Commercial AMW007/ZentriOS writes require the experimental opt-in;
module identity and expected acknowledgments must match. Its physical switch
may still need to be set to WLAN. A save acknowledgment does not verify a network
join. Reconnect the computer to the router network and rediscover the module.
Do not automatically retry after a timeout; saved state may be uncertain.

The official commercial procedure starts in Direct Connect, joins Celestron-###,
uses SkyPortal > Connect > Settings > Communication > Configure Access Point,
enters SSID/password, sends configuration and selects Use Access Point. Set the
module switch to WLAN, then join that router network on the controlling device.
The switch chooses network mode, not encryption.
Reference: https://celestron-site-support-files.s3.amazonaws.com/support_files/93973_Celestron%20SkyPortal%20WiFi%20Accessory_Manual_5LANG_Web.pdf

Validation: eight mocked backend tests and two focused GUI tests pass; lint passes.
ESP32 compilation, upload, actual configuration/network recovery and commercial
module interoperability remain unverified. No credentials or live configuration
were sent during implementation. The portal remains an alternative, not a prerequisite for command-based configuration.


Approach controls in both physical-module profiles are labelled Azimuth (RA/E–W) and Elevation (Dec/N–S), with Default / Reversed choices. Provisional UI convention: Default = positive (0), Reversed = negative (1). This does not assert a factory default or verified SkySafari mapping; raw interpretation remains visible in readback and confirmation. Manual jog mapping is unchanged.

**Module & Profile Selected** applies the target and profile; it does not connect.
Use Connect Motors or, for SkyQLink, Control Bridge ON. The indicator beside the
profile dropdown reflects fresh feedback (green), unconfirmed/retained state
(orange), or disconnected/failure (red). Motor release retains orange without a
live socket. There is no top connection switch. Local reference has ordinary
Connect Motors and Disconnect buttons for the same direct motor session.

Modern-module Diagnostics contains the shared latest-position readout and motor
polling/keep-alive controls. No additional socket or polling loop is created.
The legacy bridge retains its own controls on Control Bridge. Proxy mode remains
read-only. See the user guide for application and idle-release behavior.

Bridge link confirmation uses incoming valid telescope AUX traffic, including
encoder replies, independently of the per-axis jogging safety checks. With
heartbeat enabled, the confirmation window is its applied interval plus three
seconds for the reply; without heartbeat it is 60 seconds. Silence makes the
indicator orange; a terminal bridge failure makes it red. Outgoing commands and
echoes of this app's requests do not confirm the link.
